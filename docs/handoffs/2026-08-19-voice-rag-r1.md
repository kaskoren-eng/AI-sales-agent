## Finding 1 — retrieval had to become hybrid, and this was measured, not preferred

Pure vector search (`text-embedding-3-small`) over the real Hebrew KB returned **every chunk in a
flat 0.26–0.33 similarity band**. The right answer wasn't scoring low; *everything* scored the same.
The chunk literally headed `התנגדות — זה יקר` ranked **4th** for the query `זה יקר לי`, behind three
unrelated chunks. Trigram `word_similarity` scored that same pair **0.70**.

So retrieval fuses vector + trigram ranks via RRF. Two details that are load-bearing:

- **`word_similarity`, not `similarity`** — a short question against a 250-token chunk dilutes
  whole-string trigram overlap to noise (0.056 where `word_similarity` gave 0.70).
- **The lexical half is gated at 0.35.** Ungated, equal-weight fusion produced *zero* net gain: it
  rescued `זה יקר לי` but lost `כמה זה עולה`, because `כמה` appears in several unrelated chunks and
  lexical noise displaced good vector hits. With the floor, the lexical half can only ever add hits.

Progression, all on the same eval set: **80% → 80% → 90% → 100%** top-3 (baseline → ungated hybrid →
gated hybrid → gated hybrid + content fixes).

## Finding 2 — the 150ms budget cannot be met with per-turn embedding. R2 must decide.

```
total p50 252ms   =   embedding RTT ~205ms   +   DB ~46ms
```

Warming the socket (`EmbeddingService.warm()` exists) only helps the **first** call — the ~200ms is
the steady-state OpenAI round trip. Against the best recorded call (worst-case 1083ms, target 1500ms)
per-turn embedding lands ~1330ms: inside the MVP target, but it spends most of the remaining headroom
on every question.

**Recommendation:** prefetch at call start (the plan's tier-2 idea). Retrieval then costs the **~46ms
DB half** on the critical path, and the embedding is paid during the greeting. This is a decision for
Koren before R2 wires injection.

## Finding 3 — chunking, and a KB-authoring rule that generalises to every tenant

- **Sections must be hard boundaries.** Token-budget packing produced chunks straddling unrelated
  sections, and chunks starting mid-section with no heading. Those headless fragments then ranked
  top-3 for nearly every question while answering none. Every chunk now carries its section heading.
- **Hebrew homographs matter.** `כמה זה עולה` ("how much does it cost") was matching
  `השירות עולה לאוויר` ("the service goes live") — same verb. Rewriting the KB to
  `נכנס לפעולה` fixed it. Similarly, headings phrased the way callers actually ask
  (`תהליך ההקמה — כמה זמן לוקח להקים את השירות`) turned two misses into hits.
- **Root morphology defeats both retrievers.** `להקים` vs `ההקמה`, `לצאת` vs `יציאה` — neither
  trigrams nor this embedding model bridge Hebrew roots. Content phrasing is the cheap fix; a
  Hebrew-aware lexical normaliser is the expensive one. Not needed at 100% top-3.

**R3 implication:** the dashboard's Knowledge page must teach this, not just accept uploads. A KB
written as internal notes retrieves badly; one written in the caller's own words retrieves well.

## Questions for architect

1. **Pricing numbers are unconfirmed.** `docs/gtm/pricing-model.md` marks its own figures as an open
   decision (`החלטה פתוחה שחוסמת את הצעת המחיר`, dated 30.07.2026). They are seeded in a **separate**
   document (`clickscales-pricing-he.md`) so they can be revoked alone. **R2 must not go live on a
   real call until these are confirmed** — the agent would quote them aloud.
2. **Prefetch-at-call-start vs per-turn embedding** (Finding 2). My recommendation is prefetch.
3. **R2's Layer 1 should reuse `CallStateMachine`**, not build a parallel `call_phase` tracker — it
   already exists, is production-live, has 19 tests, and already advances to `scheduling` on
   `check_calendar_availability`. Its `stage` is monotonic and is now an analytics contract persisted
   to `call_learnings.analysis`, so "back to discovery if booking is abandoned" needs a **derived
   non-monotonic `ragActive` getter**, not a mutation of `stage`.
4. **The utterance gate must skip acknowledgments, not non-questions.** Hebrew objections are
   statements (`זה יקר לי`, `אני לא חושב שAI יכול`) — gating on "isn't a question" would suppress
   exactly the retrievals the objection content exists for. Gate on a closed list: כן / בסדר / אוקיי / תודה.
5. **Injected `[KNOWLEDGE]` messages must be append-only.** Caching matches the longest common
   *prefix*: appending and leaving prior injections in place keeps it; replacing last turn's block
   breaks the prefix at the first injection and loses the cache from there — the exact failure the
   plan is designed to avoid. Recommend append-and-keep plus chunk dedup (stable prefix, bounded
   growth, no repetition). Note `VOICE_MAX_HISTORY_ITEMS` defaults to 0 (no trim); if trimming is ever
   enabled it can evict knowledge messages and bust the prefix.

# Addendum — Phase R2 (agent integration), same day

**Commit:** `d2409d1` · Flag-off is byte-identical (golden fixtures untouched) · 910 tests pass (+37)

## The plan's injection point would have killed preemptive generation

D3 puts injection in `onUserTurnCompleted`. LiveKit builds a draft reply from the **interim**
transcript, snapshotting `agent.chatCtx`, and at turn commit keeps it only if
`preemptive.chatCtx.isEquivalent(chatCtx)` still holds (`agent_activity.js:1711`). Mutating the
context in that hook fails the check on **every grounded turn** — the same bug already documented in
`agent.ts`'s class comment (15 discarded drafts in one 4-minute call). The cost far exceeds the
~250ms retrieval the design was protecting.

**Resolution: retrieve speculatively on interim transcripts**, while the caller is still speaking.
The knowledge is in context *before* the snapshot, so the draft survives — and the ~205ms embedding
RTT is spent on speech the caller has not finished producing. This supersedes the
prefetch-at-call-start recommendation in the R1 handoff above: it is strictly better, because it
hides the latency *and* keeps per-utterance relevance.

## Deliberately NOT shipped: the slim 400-word prompt core

R2 in the plan bundles the injection plumbing with the prompt rewrite. Splitting them is a
methodology call, and the same one this repo made for the VAD sweep and the history-trim experiment:
the prompt rewrite changes **what she says**, the plumbing changes **what she knows**. Shipped
together, a quality regression on a test call cannot be attributed to either. The `ragEnabled`
parameter and the grounding slot are already in place, so the slim core is an isolated follow-up
(R2b) that can be A/B'd against the current prompt on its own.

## What is still unmeasured, and how to measure it

**Does the preemptive draft actually survive?** The design says yes; only a real call proves it.
LiveKit logs `using preemptive generation` on success and
`preemptive generation enabled but chat context or tools have changed after onUserTurnCompleted` on
failure. With RAG on, run a call and count them via `npm run agent:logs`. Alongside, `rag_turn` lines
carry `embedMs / dbMs / totalMs / injected / deduped` per turn, and `rag_skipped` carries the gate
reason. If the warning appears on grounded turns, the fallback is to inject only on turns where no
draft is in flight and accept the loss there.

# Addendum 2 — the slim prompt (R2b), same day

**Commit:** `461db06` · Flag `VOICE_SLIM_PROMPT`, default false, requires RAG · 916 tests pass

## The 300–400 word target is not reachable, and here is the arithmetic

| Part of the prompt | Words | Can it move to the KB? |
|---|---|---|
| FAQ bank + objection playbook | ~470 | **Yes** — this is knowledge |
| `businessProfile` block (per tenant) | ~180 | **Yes** — and it must, see below |
| CRITICAL SECURITY RULES | 325 | **No** — pinned by 20 injection tests |
| Step 4 booking mechanics | 519 | **No** — every line written after a real call failure |
| Role, call flow, speech rhythm, Steps 1–3, handoff, opt-out, hold | ~1,500 | **No** — behaviour, not knowledge |

Security + booking alone are **844 words**. A 400-word prompt means cutting those two, which the plan
itself forbids ("written in blood") and which the test suite enforces. Even the plan's softened
estimate — "the knowledge-free core lands around 400–500 words" — is off by roughly 4×: the
knowledge-free core is ~2,360 words.

## What the flag actually delivers

```
default persona    2832 → 2501 words  (-11.7%)
realistic tenant   3010 → 2501 words  (-16.9%)
```

**The win is not the percentage.** It is that the removed words were irrelevant on nearly every turn
and are replaced by the 2–3 chunks that turn actually needs. That was the plan's own rationale, and it
survives the word-count target being wrong.

## The `businessProfile` removal is the important half

`settings.businessProfile` carries pricing, product description and "common objections and how to
answer them" — **the same facts the KB now serves**. Leaving both in place gives every tenant two
sources of truth for the price the agent says out loud, and the prompt copy is the one nobody
remembers to update. This closes the overlap flagged in the R1 handoff. There is a test asserting the
price appears in the full prompt and not in the slim one.

## Coupling, enforced in code

`slimKnowledge` is tied to the injector object, not to the flag: with the knowledge gone and nothing
retrieving it, she simply cannot answer. Enforced in `agent.ts` rather than documented as an operator
rule, because the failure is silent — the call sounds fine right until the first question she should
have been able to answer.

## Open risk for the first test call

The phase gate closes RAG during `scheduling`/`closing`. With the slim prompt on, an objection or FAQ
raised **mid-booking** has neither prompt content nor retrieval until the two-turn stall re-opens the
gate. Two candidate fixes, neither applied yet because this should be observed before it is tuned:

1. Open the gate during booking when `slimKnowledge` is on (retrieval is speculative now, so the
   latency argument for the gate is much weaker than when the plan was written).
2. Keep the gate and accept the stall delay.

Watch for it in the first slim call: a `rag_skipped` line with `reason: "phase_gate"` on a turn where
the caller asked a real question is the signature.
