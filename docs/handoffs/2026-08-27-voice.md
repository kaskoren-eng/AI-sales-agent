## The incident

**Outbound calling was dead in production, silently, and had been.** A test lead produced
`event="outbound_call_placed"` in the logs and no phone call.

Root cause: **`LIVEKIT_SIP_OUTBOUND_TRUNK_ID` was never set on the Railway service** — it had no
SIP variables at all. `initiateOutboundCall` read it, found nothing, and returned
`{ callId: 'skipped' }` *without throwing*:

```ts
const trunkId = this.env.LIVEKIT_SIP_OUTBOUND_TRUNK_ID;
if (!trunkId) return { callId: 'skipped' };   // ← returns
```

Nothing downstream inspected the result shape, so:

- `flow-executor.worker.ts:291` logged `outbound_call_placed` on every lead, and
- `POST /api/v1/calls/outbound` answered `{ ok: true, callId: 'skipped' }` to the dashboard.

Not Zadarma. The trunks were healthy the whole time: outbound `ST_8s6N3DqUVtWw`
(sip.zadarma.com, +972555070922), inbound `ST_V5CXE6L5539t`, dispatch rule `SDR_GHNgzGi4CB4n`,
agent `CA_azGQ9uaLxpot` deployed 2026-08-26.

**Inbound was never affected** — `LIVEKIT_SIP_INBOUND_TRUNK_ID` is read only by
`admin/sip-trunk.service.ts`; inbound routing happens on LiveKit's side via the dispatch rule.

### This makes the production call count unreliable

Local `.env` has the correct trunk id, so calls driven from a dev server always worked. Calls
driven from Railway never did. **Any "production call" on record was almost certainly initiated
from someone's machine, not from prod** — worth re-checking before
`phase-6-verification-checklist.md` Layer 6 (10 real calls) is judged.

## Fixed

**Config (already live).** Set on Railway service `AI-sales-agent`:
`LIVEKIT_SIP_OUTBOUND_TRUNK_ID=ST_8s6N3DqUVtWw` and `LIVEKIT_SIP_INBOUND_TRUNK_ID=ST_V5CXE6L5539t`.
Verified: the next test lead produced a genuinely connected call — room
`call-out-ee6fa9df…` with `agent-AJ_5PMBpvHx88eL` and `lead-+972509788845` both ACTIVE and
publishing. Note the failing attempt returned in milliseconds while the working one took ~10s,
because `waitUntilAnswered: true` actually waits for pickup — that timing gap is a usable signal.

**Code (`11ff507`, unmerged).**

1. `initiateOutboundCall` now **throws** `AppError(503, 'SIP_TRUNK_NOT_CONFIGURED')` instead of
   returning the skip marker, so a make_call step fails into the DLQ where someone finds it.
   Callers need no change — the retry/DLQ path already exists.
2. It also `console.error`s `event: 'dial_failed_no_trunk'` with tenantId + leadId — the throw is
   swallowed by BullMQ retry, so without the log the only trace is a job failure reason.
   Deliberately **not** logging `to`: that is a lead's phone number.
3. `server.ts` (additive) logs a loud `event: 'outbound_dialling_disabled'` **at boot** when the
   service constructs but no trunk id is set. The service is perfectly constructible without one —
   it is read only inside `initiateOutboundCall` — so a trunk-less instance looks healthy until a
   lead goes uncalled. This line is what would have caught the missing var on the deploy that
   dropped it.
4. New `voice-livekit.dial-config.test.ts` (5 cases), including one asserting the result can never
   again be the success-shaped `{ callId: 'skipped' }`, and one treating an empty-string trunk id
   as unset (Railway returns `''` for a cleared variable).

Full suite green: 95 files / 970 tests. `npm run build` clean.
