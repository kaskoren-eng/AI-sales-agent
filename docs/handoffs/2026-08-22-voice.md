## What R2.1 fixes, and how

R2 appended every retrieval to `agent.chatCtx` permanently: context grew **2,742 → 8,306 tokens**
across four minutes, monotonically. TTFT tracks context size, so the slim prompt ended the call
slower than the full prompt it replaced.

**The mechanism was already in the SDK.** `agent_activity.cjs:1883` does `chatCtx = chatCtx.copy()`
immediately before calling `llmNode`, so that hook edits a per-inference copy. Verified before being
relied on. Two consequences, both load-bearing:

- session history stays clean → injection overhead is **flat**, not cumulative;
- `agent.chatCtx` is untouched → the preemptive equivalence check never sees the edit and the draft
  **survives**. R2 spent a whole cycle fighting that check; here it does not apply.

## The phase-gate question (asked explicitly, answered from the log)

**The gate was engaging correctly. Its definition of "stalled" was wrong.**

`ragActive` reopens retrieval at `scheduling` after `BOOKING_STALL_TURNS = 2` user turns with no
scheduling tool. On the real call, between `check_calendar_availability` and `book_meeting` there
were ~10 turns collecting a name, a phone number (asked **4 times**) and an email (asked **3 times**).
Each fired `capture_lead_info`; none fired a *scheduling* tool. So the rule concluded the booking had
been abandoned and reopened retrieval for the rest of the call — the 14 lookups at `stage=scheduling`.

Fixed at the cause, not masked: `capture_lead_info` now resets the stall counter once booking has
started. Collecting a detail *is* progress toward the booking; a caller who has genuinely gone back to
asking questions does not hand over his email address. `answering_agent` would have hidden this.
